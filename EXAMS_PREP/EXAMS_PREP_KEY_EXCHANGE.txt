pkeyopt are options that we can use to create the key

- rsa_keygen_pubexp: Exponent(-pkeyopt rsa_keygen_pubexp:65537 Sets the RSA public exponent to 65537.)
- -out: destination file to PEM format (Privacy Enhanced Mail)
- rsa_keygen_primes: Set the prime factors(-pkeyopt rsa_keygen_primes:2 Sets the number of prime

You are NOT manually creating p, q, or d OpenSSL does everything internally
You only control:
- key size (2048 bits)
- public exponent (3)

Privacy Enhanced Mail (PEM). PEM is a file format that may consist of a certificate for private/public key.

In asymmetric cryptography (public/private key systems), the process is:
- The private key is generated first (randomly)
- The public key is mathematically derived from the private key
- But it is designed so thaty ou cannot reverse the public key to get the private key
So:
✔ Private key → used to generate public key
❌ Public key does NOT generate private key
❌ Neither “creates” the other in a reversible way
Private key  ──(math function)──> Public key

In symmetric cryptography, there is no public/private key pair.
- There is only one shared secret key
- The same key is used for both encryption and decryption
- Both parties must already know the same secret key

Key K
   ↓
Encrypt(M, K) → Ciphertext
   ↓
Decrypt(Ciphertext, K) → M

Who creates what?
- One side generates the secret key (randomly or via key exchange)
- Then that same key is shared securely with the other side

But:
- The key is not split into public/private parts
- It is just one shared secret
⚠️ Main challenge The hardest part is:
How do both sides safely get the same key without someone stealing it?
That’s why systems like HTTPS use:
- asymmetric crypto (RSA/ECC) to exchange the key
- then switch to symmetric crypto (AES) for speed

A
WHAT A DOES:
1. A writes the message
M = "This is for you"

2. A hashes the message: A one-way function that converts data into a fixed-length fingerprint (no recovery of original data).
H = SHA256(M)
This produces something like:
[9f7a...ab12 (the actual hash is much longer)}

3. A signs the hash: The digital signature is the encrypted Hash
        A cryptographic proof created with a private key to verify authenticity and integrity of data.
A does:
Signature = Sign(A_private_key, H):
- The private key is not attached to the message.
- The private key never leaves A's computer.
- The result is a signature that can later be verified using A's public key.
- A does not add the private key. A adds the signature, which is a piece of data computed using the private key (Message + Signature).
- The signature is usually a sequence of bytes (often represented as hexadecimal or Base64 text). 
    It looks like random data, for example:

Message:
"This is for you"

H = SHA256(M)
This produces something like:
9f7a...ab12 (the actual hash is much longer)
[Signature:
7F3A91C4E8D2...}

The signature is the result of a mathematical operation involving:
- The hash of the message
- A's private key

AT THIS STAGE ANYONE WITH A'S PUBLIC KEY CAN VERIFY IT.
--> BUT A wants only B to be able to read the message.
↓
4. A encrypts the message for B: The process of converting readable data (plaintext) into unreadable form using a key(B_public_key).
More precisely:
Ciphertext = Encrypt(B_public_key, M)
Only B can decrypt it because only B has: B_private_key

Ciphertext = Encrypt(B_public_key, [M, A_Signature])
- M is included in plaintext form inside the encryption
- The hash (H = SHA256(M)) is only used to create the signature
- B will recover M after decryption and then recompute the hash to verify integrity

Why not encrypt the hash instead of M?
Because:
- The hash alone is not the message
- B needs the actual message to read it and verify it
- The signature already “binds” the hash to A’s private key

5. A sends: Ciphertext(The unreadable output produced after encryption.)
{Ciphertext, Signature}

B
WHAT B DOES

1. B decrypts: Ciphertext → Decrypt using B_private_key: The process of converting encrypted data back into readable form using a key(B_private_key).
B uses B_private_key to decrypt.
M = Decrypt(B_private_key, Ciphertext)
[M, A_Signature] = Decrypt(B_private_key, Ciphertext)

Now B can read: This is the first moment B can read the entire message.
"This is for you"

This only works if the Ciphertext was encrypted with B’s matching public key
If ciphertext is wrong/tampered Decryption fails OR produces garbage data

[M, A_Signature]
This is not “computed” — it is revealed after successful decryption.

If decryption succeeds → B literally obtains:
- M (message)
- A_Signature
If decryption fails → B never reaches this step

Both the message and the signature are protected inside the ciphertext.
When B decrypts:
M = Decrypt(B_private_key, Ciphertext):

[M, A_Signature] = Decrypt(B_private_key, Ciphertext)
        ↓
[M, A_Signature]
B gets both back, the message M and the A digital signature A_Signature

2. B hashes the decrypted message
H1 = SHA256(M)
B computes this himself.

Why? To verify the message wasn't changed.
- B is not given H
- B recomputes it from the received message

B creates his own hash from the plaintext message M, but only after decrypting it.

3. B verifies the A_signature
B never sees A's private key.
B has A_public_key and receives A_Signature

Then B performs: use A_public_key to decrypt A digital signature(A_Signature)
Verify(A_public_key, A_Signature)
Verify(A_Signature, B_Hash, A_public_key)

This verifies that the signature could only have been created by someone possessing A's private key.
The A_signature is a cryptographic proof that allows B to verify that the message was signed by A 
    and has not been modified.

4. B compares hashes
Verify(A_Signature, SHA256(M), A_public_key) = TRUE
Verify(Sign(SHA256(M), A_private_key), SHA256(M), A_public_key) = TRUE

Check: does Signature match H using A_public_key?
The signature corresponds to the hash of the message under A’s public key. B recomputes SHA256(M), 
    and verification succeeds if the signature was created using A’s private key over that same hash.

Conceptually:
H1 = SHA256(received_message)
H2 = hash recovered/checked from signature


Then:
H1 == H2
If true:
 Message wasn't modified.
 Signature is valid.
 Message came from A.

Your question: How does B know which cipher to use?
Good question.
Usually the protocol specifies it. For example:

B knows because:

3. Or the certificate indicates the signature algorithm.

Examples:
- HTTPS/TLS
- PGP
- SSH

all negotiate algorithms before data is exchanged.
Your question: Do A and B have to know the same hash?
Yes.
Both sides must know:
SHA256

If A uses SHA256 and B uses SHA1 the hashes won't match and signature verification fails.

One final correction: when people say "decrypt with the public key" while discussing signatures, 
they are usually simplifying how RSA signatures work mathematically. In modern cryptography, think of it as:
Encryption: Public key → Private key
Signature: Private key → Public key verification
That mental model is much safer and closer to how real systems operate today.
