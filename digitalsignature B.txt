PUBLIC KEY ENCRYPTION AND DIGITAL SIGNATURE USING OpenSSL

Scenario:
Two people A & B
Both would like to communicate some confidential information
Both will generate their public keys and private keys
They will use RSA as the public key cryptography algorithm to generate the keys (RSA (Rivest–Shamir–Adleman) is a public-key cryptosystem)
User A will create a confidential message, sign that message to create a digital signature (for the message). A will also encrypt the message using RSA algorithm. A will send the message to B. 
Upon reception of the message, B will decrypt the message and also verify the hash (in the digital signature), making sure they came from A.

Note the following:
A uses his private key to produce his public key
B uses his private key to produce his public key
A uses his private key to produce a digital signature
The digital signature is the encrypted Hash. So A uses his private key to encrypt the Hash, resulting in a digital signature 
A uses B's public key to encrypt the message
A sends the digital signature and the encrypted message to B
B uses his (i.e. B's) private key to decrypt the message
B uses A's public key to decrypt the digital signature (created by A) (When he does so he gets the HASH sent by A)
B uses A's public key to verify the digital signature (created by A) (he will do so by encrypting the (decrypted) message (again) using A's public key.
If the digital signature sent by A to B is similar to the digital signature B produces, then the digital signature is verified
Both A and B should never know the other's private key
Both A and B should know each other's public key, and the cryptography algorithm used (e.g. RSA)

Note in the steps above, A can also combine (the digital signature and the message) and encrypt them together using B's public key (let us call that
DM). A will then send the DM to B.
If done that way, then B will have to use his (i.e., B's) private key to decrypt the (DM ). Note, B will now get the digital signature and the message).
Further, B will have to use A's public key to decrypt the digital signature (sent by A), which he has just extracted from the DM.
B will then use the extracted Message and A's public key to reproduce the Digital signature. If his digital signature = A's digital signature
Then the digital signature is verified and the message has not been tampered with.

The core mathematical operation in RSA encryption and decryption is modular exponentiation. This involves raising a number to a power and then taking the modulus. For instance, during encryption, the plaintext message m is raised to the power e and then taken modulo n. Similarly, during decryption, the ciphertext c is raised to the power d and then taken modulo n.

RSA Key Generation: RSA (Rivest–Shamir–Adleman) is an asymmetric encryption algorithm that relies on two keys: a public key for encryption and a private key for decryption. 
Public Key Components: The public key consists of two values: the modulus (n) and the public exponent (e). 
Modulus (n): The modulus is the product of two large prime numbers (p and q). 
Public Exponent (e): The public exponent is an odd integer, typically small (e.g., 65537). Public exponent (e) is the exponent used on signed / encoded data to decode the original value.
Why Small Exponents? Using a small public exponent (like 65537) makes the encryption and signature verification processes computationally faster due to the properties of modular exponentiation. 
Common Values: While 65537 is the most common choice, other small odd numbers like 3, 5, 17, and 257 are also used. 
Security Considerations: While small exponents offer efficiency, they can also be vulnerable to certain attacks if not used with proper padding schemes. 
Private Exponent (d): The private exponent (d) is calculated based on the modulus (n) and the public exponent (e) and must be kept secret.

(step 9)

Then A, creates a digital signature using his Private key and the messageAB.txt
Note, the following instructions would produce the hash, then encrypt it to get a digital signature. 
A digital signature is encrpted (hash or Digest). The hash is produced using A's private key and the message - i.e., messageAB.txt).
You can see we did not use "294f11ebb7f49a5b08a584c18d9c26a2cb9cfdb5" anywhere in the following instruction.  
The instruction below generates it and then encrypts it.
                                                           
┌──(root💀mikayili)-[/home/mk001/opensslnotes]
└─# openssl dgst -sha1 -sign privkey-A.pem -out signature.bin messageAB.txt

(step 10)

In the step above, A encrypted the "Hash or digest" (NOT the message), using his "Private key" to get a digital signature. However,  
A will have to send to B 2 things (i) the digital signature (ii) the message (messageAB.txt). Since 
he does not want the message to be hacked, A encrypts it also, but this time using B's "public key".  

Encrypt the message (messageAB.txt) using B's public key. The encrypted message is saved in file Ciphertext.bin
(NOTE: IN SOME CASES ONE MAY ENCRYPT THE MESSAGE + DIGITAL SIGNATURE) using B's public key  (see Digital signature lecture slides). However,
in the present demo, we did not do that.  
                                                                                                           
┌──(root💀mikayili)-[/home/mk001/opensslnotes]
└─# openssl pkeyutl -encrypt -in messageAB.txt -pubin -inkey pubkey-B.pem  -out ciphertext.bin

(step 11)

When the message is received by B, B uses his private key to decrypt the message in the document ciphertext.bin, and the result is stored in 
file 'received-message.txt'.

                                                                                                           
┌──(root💀mikayili)-[/home/mk001/opensslnotes]
└─# openssl pkeyutl -decrypt -in ciphertext.bin -inkey privkey-B.pem -out received-message.txt

(step 14)

Now B would like to verify the digital signature. He uses A's public key, and the received-message.txt  to verify the "HASH" or
("DIGEST") (i.e., to reproduce the Hash A sent to him and confirm if they are the same). The following 
instruction will first decrypt the digital signature to get the HASH (A sent, remember the Hash was included in the digital signature).
B will then use A's public key and the message A sent (i.e. received-message.txt), to reproduce the Hash
if the two Hashes are the same, then verification is OK.
                                                                                                           
┌──(root💀mikayili)-[/home/mk001/opensslnotes]
└─# openssl dgst -sha1 -verify pubkey-A.pem -signature signature.bin received-message.txt              2 ⨯
Verified OK

The digital signature is verified - so everything is correct.


If say you used an incorrect Key, verification will fail.
