DNS over TLS (DoT) is a security protocol that encrypts your device's Domain Name System queries using Transport Layer Security
* **DoT (DNS over TLS):** Encrypts DNS queries using TLS, usually on **port 853**.
* **DoH (DNS over HTTPS):** Encrypts DNS queries inside HTTPS, usually on **port 443**.
* **DNSSEC:** **Authenticates DNS responses** to prevent DNS spoofing/tampering; it **does not encrypt** DNS queries.
* **DNSCrypt:** Encrypts and authenticates DNS traffic between the client and resolver using the **DNSCrypt protocol**.
* **Quad9:** A **public DNS resolver service** (`9.9.9.9`) that provides security features such as **malicious-domain blocking**, with support for encrypted DNS.

**Simple distinction:**
**DoT/DoH/DNSCrypt = protect DNS traffic** 🔒
**DNSSEC = verify DNS authenticity** ✅
**Quad9 = a DNS resolver/service that can provide these protections**.

In short: Both encrypt DNS, but DoT uses dedicated DNS traffic (853), while DoH uses HTTPS (443) and is generally harder to distinguish from regular web traffic.

If you're comparing **DoT, DoH, DNSSEC, DNSCrypt, and Quad9**:

| Technology   | Hides SNI? | Why                                                             |
| ------------ | ---------- | --------------------------------------------------------------- |
| **DoT**      | ❌ No       | Encrypts DNS, but not the HTTPS connection's SNI                |
| **DoH**      | ❌ No       | Encrypts DNS queries, but normal HTTPS SNI can still be visible |
| **DNSSEC**   | ❌ No       | Provides DNS authentication, not encryption                     |
| **DNSCrypt** | ❌ No       | Encrypts DNS traffic, not TLS SNI                               |
| **Quad9**    | ❌ No       | It is a DNS resolver; using Quad9 does not by itself hide SNI   |

**Important:** **DNS encryption ≠ SNI encryption.**

To hide the destination hostname in the TLS handshake, you need **ECH (Encrypted Client Hello)**. With ECH, the **SNI is encrypted** (more precisely, the `ClientHello` containing the real server name is encrypted).

ECH is implemented **in the TLS/HTTPS connection**, not inside DNS itself.

**ECH (Encrypted Client Hello) *does* hide the real SNI from network observers when it is properly supported and used.** Your notes contain some accurate observations mixed with incomplete or outdated understandings of how it works.

### How ECH actually works
- The client builds two ClientHellos:
  - **ClientHelloOuter** (sent in cleartext): Contains a *public/cover* SNI (often a generic name belonging to the CDN or hosting provider, e.g. `cloudflare-ech.com`). This is what passive observers (ISP, network monitors, etc.) see.
  - **ClientHelloInner** (encrypted): Contains the *real* destination SNI plus other sensitive fields (ALPN, etc.). Only the server that holds the corresponding private key can decrypt it.
- The encryption key for the inner ClientHello is published by the server in DNS (HTTPS/SVCB records). Clients normally fetch this via encrypted DNS (DoH/DoT) so the key distribution itself is not visible in cleartext.
- Result: On-path observers see traffic going to the public name / shared IP, not the specific site the user intended. This is the privacy goal of ECH.

Packet captures and testbeds consistently show the real hostname replaced by the outer/public name when ECH is active.

### Where the limitations and common confusions come from
- **ECH is not universal.** Both the browser *and* the server/CDN must support it. Many sites still do not publish ECH configs, so the connection falls back to ordinary TLS with cleartext SNI. Adoption has grown (especially on major CDNs), but it is far from complete.
- **Outer SNI is still visible.** That is by design. The outer name is deliberately generic so that many real sites can hide behind the same public name (creating an anonymity set).
- **IP address remains visible.** If a site has a unique IP, the destination can still be inferred regardless of SNI/ECH.
- **DNS must also be protected.** Plain DNS queries reveal the domain before the TLS handshake even starts. DoH/DoT + ECH together close both major leaks. DNS-over-HTTPS alone does *not* hide the SNI; that is why ECH exists.
- **Organisation-managed networks** can still force their own DNS, block DoH, or inspect/terminate TLS (corporate proxies, etc.). Browser DNS settings can be overridden in managed environments.
- **VPN / full tunnel** hides everything (DNS + TLS handshake + destination IP from the local network) because the traffic never leaves the encrypted tunnel in a form the local observer can parse. ECH only protects the TLS metadata; a VPN protects the entire path.

### Summary of your points
| Claim | Reality |
|-------|---------|
| “ECH with DNS, SNI hello can be seen” | Only the *outer* (public) SNI is visible. The real one is encrypted. |
| “ECH is supposed to hide but does not” | It *does* hide the real SNI when both ends support it. Incomplete adoption is the main practical gap. |
| DNS can be hidden but not SNI | Incorrect once ECH is active. DoH hides DNS; ECH hides the real SNI. |
| Only VPN hides SNI | VPN is more comprehensive, but ECH specifically targets and encrypts the SNI field. |
| “TLS queries cannot be hidden, even the latest” | The sensitive parts of the ClientHello *are* hidden by ECH. The outer handshake is still visible by design. |

ECH is now an official standard (RFC 9849) and is the successor to the earlier ESNI effort. It closes the long-standing plaintext-SNI leak in TLS 1.3, but it is not a complete anonymity solution on its own—combine it with encrypted DNS and, when stronger protection is needed, a VPN.


**The outer SNI (and the ClientHelloOuter) is still sent in cleartext by design.** That is why you still see *a* hostname in the TLS “hello” message even when ECH is working.

### Why this happens

ECH does **not** encrypt the entire first TLS message. It uses a split design:

1. **ClientHelloOuter** – sent in **plaintext**
   - Contains a *public / cover* SNI (for example `cloudflare-ech.com` or another generic name published by the server/CDN).
   - Also contains the encrypted inner ClientHello as an extension.
   - This is what network observers, ISPs, or packet captures see.

2. **ClientHelloInner** – **encrypted**
   - Contains the *real* destination SNI you actually want to reach.
   - Only the server that holds the matching private key can decrypt it.

So the “hello” is still exposed, but the sensitive part (the real domain) is hidden inside the encrypted extension. What you see is deliberately a non-sensitive public name.

### Why the protocol keeps an outer cleartext SNI

- **Compatibility**: Existing servers, load balancers, and middleboxes expect a normal TLS ClientHello with an SNI. Sending a completely empty or missing SNI would break many deployments.
- **Routing / key selection**: In multi-tenant setups (CDNs, shared hosting) the outer SNI tells the client-facing server which ECH configuration/key to try.
- **Graceful fallback**: If the server cannot decrypt the inner ClientHello (wrong key, outdated config, etc.), it can still complete a normal handshake using the outer public name and present a valid certificate for that name.
- **Anonymity set**: Many real sites share the same outer public name. Observers only learn “someone is talking to this CDN/provider”, not which specific site.

### Bottom line

- You will **always** see *some* SNI in the clear when looking at the TLS handshake.
- With working ECH that SNI is the **public/cover name**, not the real destination.
- The real destination is encrypted and only visible to the intended server.

That is why tools still show an SNI “hello” even when ECH is active — the protocol intentionally leaves a harmless outer name visible so the rest of the internet infrastructure continues to work.

But there's an important distinction between **DoT/DoH/DNSCrypt, DNSSEC, and Quad9**.

### 1. DoT — DNS over TLS

**DoT protects the DNS communication channel.**

Normally:

```text
User → DNS resolver
       DNS query
```

With DoT:

```text
User
  |
  | encrypted TLS connection
  v
DNS Resolver
```

So someone monitoring the network has a harder time seeing the DNS queries.

**Purpose:** confidentiality and integrity of the connection to the resolver.

---

### 2. DoH — DNS over HTTPS

DoH does essentially the same broad job—protecting DNS queries—but sends DNS through **HTTPS**.

```text
User
  |
  | HTTPS
  v
DoH Resolver
```

This can make DNS traffic blend in with ordinary HTTPS traffic.

**DoT vs DoH:**

|                      | DoT                   | DoH                   |
| -------------------- | --------------------- | --------------------- |
| Transport            | TLS                   | HTTPS                 |
| Typical port         | 853                   | 443                   |
| Encrypts DNS traffic | Yes                   | Yes                   |
| Main purpose         | Private DNS transport | Private DNS transport |

---

### 3. DNSCrypt

DNSCrypt is another protocol designed to **authenticate and encrypt DNS communication between a client and a DNS resolver**.

Conceptually:

```text
Client
   |
   | encrypted/authenticated DNS
   v
DNSCrypt Resolver
```

So you can think of DoT, DoH and DNSCrypt as **different ways of protecting the path between the DNS client and resolver**.

---

### 4. DNSSEC

DNSSEC is different.

It isn't primarily about hiding the DNS query.

Instead, DNSSEC allows a resolver to verify:

> **"Did this DNS answer really come from the legitimate DNS zone, and was it modified?"**

For example, suppose you ask:

```text
www.example.com → 203.0.113.10
```

DNSSEC provides cryptographic signatures that allow validating resolvers to verify the authenticity of the DNS data.

So:

```text
DoT / DoH / DNSCrypt
        ↓
Protect the DNS communication channel

DNSSEC
        ↓
Protect/authenticate the DNS data itself
```

They can therefore be used **together**.

---

### 5. Quad9

**Quad9 is not a protocol.**

It's a **public DNS resolver service**.

So your computer could be configured to use Quad9 as its DNS resolver, while the connection to Quad9 could use a supported encrypted DNS protocol.

Conceptually:

```text
Your computer
      |
      | DoH / DoT
      v
   Quad9
      |
      | DNS resolution + security filtering
      v
Authoritative DNS
```

Quad9 is also known for blocking domains associated with known malicious activity.

In DNS, they are **very different**:

* **`testme.example.com`** → a **hostname/subdomain (FQDN)**. DNS can resolve this name to an IP address.

  * Example: `testme.example.com → 192.168.1.10`

* **`example.com/testme`** → **not a DNS name**. The `/testme` part is a **URL path**, handled by the web server.

  * DNS only resolves `example.com → IP`
  * The web server then handles `/testme`.

So:

```text

└─────── DNS/FQDN ───────┘

https://example.com/testme
       └─ DNS ─┘ └─ URL path ─┘
```

**Simple rule:**
**DNS deals with domain/hostnames; HTTP/HTTPS deals with paths such as `/testme`.**
